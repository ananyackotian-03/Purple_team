## Mandate & Fundamental Security Principle

> **CRITICAL SECURITY INVARIANT**
> **"The real production application is NEVER modified by SentinelForge. All remediation operations execute exclusively against isolated clones."**
>
> **THE LLM IS AN UNTRUSTED PROPOSAL GENERATOR. IT PROPOSES REMEDIATIONS; DETERMINISTIC INFRASTRUCTURE VALIDATES AND APPLIES.**

Every remediation proposal generated by the LLM MUST pass through the following deterministic authorization pipeline before any file is modified:

$$\text{Vulnerability} \longrightarrow \text{Finding} \longrightarrow \text{Root Cause} \longrightarrow \text{LLM Remediation Proposal} \longrightarrow \text{Schema Validation} \longrightarrow \text{RemediationPolicy} \longrightarrow \text{Clone Creation} \longrightarrow \text{Apply Fix} \longrightarrow \text{Build/Test} \longrightarrow \text{Red Retest} \longrightarrow \text{VERIFIED / ITERATE / FAIL}$$

## 1. Vulnerability Model

### 1.1 VulnerabilityFinding

A `VulnerabilityFinding` represents a confirmed application vulnerability discovered by the Red Agent during an authorized exercise. NOT every failed attack or detection gap constitutes a vulnerability.

```python
class VulnerabilitySeverity(str, Enum):
    CRITICAL = "CRITICAL"
    HIGH = "HIGH"
    MEDIUM = "MEDIUM"
    LOW = "LOW"
    INFORMATIONAL = "INFORMATIONAL"

class VulnerabilityConfidence(str, Enum):
    CONFIRMED = "CONFIRMED"     # Red Agent reproduced with evidence
    PROBABLE = "PROBABLE"       # Strong indicators, not fully reproduced
    SUSPECTED = "SUSPECTED"     # Pattern match, requires verification

class VulnerabilityStatus(str, Enum):
    OPEN = "OPEN"                       # Newly discovered
    ROOT_CAUSE_IDENTIFIED = "ROOT_CAUSE_IDENTIFIED"  # Root cause analyzed
    REMEDIATION_PROPOSED = "REMEDIATION_PROPOSED"      # LLM proposed fix
    REMEDIATING = "REMEDIATING"         # Fix applied to clone, testing
    REMEDIATION_VERIFIED = "REMEDIATION_VERIFIED"      # Red retest passed
    REMEDIATION_FAILED = "REMEDIATION_FAILED"          # Fix did not work
    REQUIRES_HUMAN_REVIEW = "REQUIRES_HUMAN_REVIEW"    # Budget exhausted
    ACCEPTED_RISK = "ACCEPTED_RISK"    # Human-accepted risk (future)

class VulnerabilityFinding(BaseModel):
    finding_id: UUID
    organization_id: UUID               # Tenant isolation
    target_id: UUID                      # FK -> ApplicationTarget
    exercise_id: Optional[UUID]          # FK -> Exercise
    scenario_id: Optional[UUID]          # FK -> AdversarialScenario
    attack_technique_id: str             # MITRE ATT&CK technique
    vulnerability_category: str          # OWASP class (e.g. "A03_INJECTION")
    affected_component: str              # File/module/route affected
    evidence: str                        # Reproduction steps + output
    severity: VulnerabilitySeverity
    confidence: VulnerabilityConfidence
    root_cause_hypothesis: Optional[str] # LLM-generated root cause
    reproduction_info: str               # Exact steps to reproduce
    status: VulnerabilityStatus
    remediation_status: str              # OPEN -> IN_PROGRESS -> APPLIED -> VERIFIED
    iteration_count: int                 # Number of remediation attempts
    max_iterations: int                  # Budget cap (default: 3)
    created_at: datetime
    updated_at: datetime
    provenance: dict                     # Audit trail
```

### 1.2 Criteria for Vulnerability Classification

An observation qualifies as a `VulnerabilityFinding` ONLY when ALL of the following hold:

1. **Reproducible**: The Red Agent successfully reproduced the attack in the isolated target (exit code, output, or observable state change).
2. **Evidence-backed**: The attack produced observable evidence (stdout, filesystem state change, network response, or application behavior change).
3. **Applicable to target**: The attack targets the application itself (not just detection rules). For example: SQL injection in application code, hardcoded credentials, missing input validation, path traversal in file serving, command injection in application parameters.
4. **Not a detection gap**: A detection gap means the defense failed to observe an action. A vulnerability means the application itself is vulnerable. These are distinct Branch 1 vs Branch 2 concepts.

### 1.3 Vulnerability Classification Decision Tree

```
Red Agent executes attack scenario
         │
         ▼
    Attack succeeds? ──── NO ──── Not a vulnerability (attack failed)
         │
        YES
         │
         ▼
    Application compromised? ──── NO ──── Not an app vulnerability
         │                            (might be detection gap only)
        YES
         │
         ▼
    Component identified? ──── NO ──── Cannot create finding
         │
        YES
         │
         ▼
    CREATE VulnerabilityFinding
```

## 2. Application Target

### 2.1 ApplicationTarget Model

An `ApplicationTarget` represents an authorized web application that SentinelForge may test. The target must explicitly declare ownership, authorization, and scope.

```python
class TargetType(str, Enum):
    LOCAL = "local"                 # Local filesystem path
    DOCKERIZED = "dockerized"       # Docker container
    REPOSITORY = "repository"       # Git repository

class TargetEnvironment(str, Enum):
    PRODUCTION = "production"       # READ-ONLY, never written
    STAGING = "staging"             # Isolated, writable
    DEVELOPMENT = "development"     # Isolated, writable
    LAB = "lab"                     # SentinelForge-managed

class ApplicationTarget(BaseModel):
    target_id: UUID
    organization_id: UUID               # Tenant isolation
    name: str                           # Human-readable name
    description: str
    target_type: TargetType
    environment: TargetEnvironment

    # Source configuration
    repository_url: Optional[str]       # Git URL (for REPOSITORY type)
    commit_sha: Optional[str]           # Pinned commit
    docker_image: Optional[str]         # Docker image (for DOCKERIZED type)
    docker_compose_path: Optional[str]  # docker-compose.yml path
    local_path: Optional[str]           # Local path (for LOCAL type)

    # Authorization
    owner_user_id: UUID                 # Who owns this target
    authorized_by: UUID                 # Who authorized testing
    authorization_expiry: datetime      # When authorization expires

    # Scope
    allowed_technique_ids: List[str]    # MITRE techniques allowed
    max_risk_level: RiskLevel           # Maximum risk allowed
    allowed_test_hours: Optional[str]   # Time window for testing

    # Network policy
    network_isolated: bool = True       # Isolated from production network
    allowed_outbound: List[str] = []    # Allowed outbound hosts/IPs

    # Status
    is_active: bool = True
    created_at: datetime
    updated_at: datetime
```

### 2.2 Production Read-Only Invariant

When `environment == TargetEnvironment.PRODUCTION`:
- SentinelForge may READ the repository/container for vulnerability analysis
- SentinelForge may EXECUTE read-only commands against the application
- SentinelForge MUST NOT write files, modify configuration, or alter state
- Remediation proposals against production targets are BLOCKED at the policy layer
- Only `STAGING`, `DEVELOPMENT`, or `LAB` targets are eligible for remediation

### 2.3 Target Authorization Validation

```python
class TargetAuthorizationValidator:
    @staticmethod
    def validate_target_access(target: ApplicationTarget, org_id: UUID) -> bool:
        # 1. Tenant isolation
        if target.organization_id != org_id:
            raise SecurityRejection(TENANT_VIOLATION)
        # 2. Target active
        if not target.is_active:
            raise SecurityRejection(TARGET_INACTIVE)
        # 3. Authorization not expired
        if datetime.now(timezone.utc) > target.authorization_expiry:
            raise SecurityRejection(AUTHORIZATION_EXPIRED)
        # 4. Environment check
        if target.environment == TargetEnvironment.PRODUCTION:
            raise SecurityRejection(PRODUCTION_TARGET_NO_REMEDIATION)
        return True
```

## 3. Target Clone

### 3.1 TargetClone Model

A `TargetClone` is an isolated, reproducible copy of an `ApplicationTarget` used for remediation testing. The clone must be fully isolated from the original target and from production.

```python
class CloneStatus(str, Enum):
    CREATING = "CREATING"
    READY = "READY"
    REMEDIATING = "REMEDIATING"
    TESTING = "TESTING"
    ROLLING_BACK = "ROLLING_BACK"
    FAILED = "FAILED"
    CLEANED_UP = "CLEANED_UP"

class TargetClone(BaseModel):
    clone_id: UUID
    organization_id: UUID               # Tenant isolation
    source_target_id: UUID              # FK -> ApplicationTarget
    source_revision: str                # Commit SHA or image tag

    # Isolated environment
    clone_type: TargetType              # Same as source
    docker_container_name: Optional[str]  # Isolated container name
    docker_network: Optional[str]       # Isolated Docker network
    filesystem_path: Optional[str]      # Isolated filesystem path

    # Network policy
    network_isolated: bool = True       # No external network access
    allowed_inbound: List[str] = []     # Only SentinelForge retest traffic
    allowed_outbound: List[str] = []    # No outbound to production

    # Resource limits
    max_cpu_seconds: int = 120          # Max CPU time per operation
    max_memory_mb: int = 512            # Max memory usage
    max_disk_mb: int = 1024             # Max disk usage

    # Secret isolation
    secrets_injected: List[str] = []    # List of injected secret names
    original_secrets_excluded: bool = True  # Production secrets never copied

    # Snapshot/versioning
    current_version: int = 1            # Monotonically increasing
    snapshot_ids: List[str] = []        # Snapshots for rollback

    # Lifecycle
    status: CloneStatus
    created_at: datetime
    updated_at: datetime
    expires_at: datetime                # Auto-cleanup deadline
    cleanup_status: str = "PENDING"     # PENDING -> IN_PROGRESS -> CLEANED
```

### 3.2 Clone Creation Requirements

1. **Isolation**: Clone runs on a separate Docker network. No communication with source target or production.
2. **Reproducibility**: Clone is created from a pinned `source_revision` (commit SHA or image tag). Same revision always produces the same clone.
3. **Secret Isolation**: Production secrets are NEVER copied. Clone uses synthetic/test secrets injected by SentinelForge.
4. **No Production Data**: Clone does not receive production databases or data. It uses synthetic test data.
5. **Resource Bounded**: Clone has strict CPU, memory, and disk limits enforced by Docker.
6. **Time Bounded**: Clone has an expiration deadline. Auto-cleanup after `expires_at`.

### 3.3 Clone Lifecycle

```
ApplicationTarget (source, READ-ONLY)
         │
         ▼
    Create Clone
         │
         ▼
    Clone READY
         │
    ┌────┴────┐
    │ Snapshot │ (v1, v2, v3...)
    └────┬────┘
         │
    Apply Remediation
         │
         ▼
    Clone REMEDIATING
         │
    Build & Test
         │
         ▼
    Clone TESTING
         │
    ┌────┴─────────┐
    │ Red Retest    │
    └────┬─────────┘
         │
    ┌────┴──────────────┐
    │ VERIFIED?          │
    │  YES → COMPLETE    │
    │  NO  → ROLLBACK    │
    │         │          │
    │    Apply Next Fix  │
    └────────────────────┘
         │
    Cleanup
         │
         ▼
    Clone CLEANED_UP
```

## 4. Remediation Proposal

### 4.1 RemediationProposal Model

The LLM generates a structured `RemediationProposal`. The LLM MUST NOT directly modify files. It proposes; deterministic infrastructure validates and applies.

```python
class RemediationProposal(BaseModel):
    proposal_id: UUID
    finding_id: UUID                    # FK -> VulnerabilityFinding
    organization_id: UUID               # Tenant isolation

    # What the LLM proposes
    root_cause: str                     # Root cause analysis
    proposed_remediation: str           # Natural language description
    affected_files: List[str]           # Files to modify
    patches: List[PatchSpec]            # Structured diffs/patches
    expected_security_effect: str       # Expected security improvement
    expected_behavior: str              # Expected application behavior post-fix
    test_plan: str                      # How to verify the fix
    rollback_plan: str                  # How to undo if fix breaks things
    risk_assessment: str                # Risk of applying this fix

    # Validation results
    schema_validated: bool = False      # Passed Pydantic schema
    policy_validated: bool = False      # Passed RemediationPolicy
    clone_validated: bool = False       # Applied and built successfully

    # Provenance
    created_at: datetime
    provenance: dict                    # Audit trail

class PatchSpec(BaseModel):
    file_path: str                      # Relative path within clone
    operation: str                      # "modify", "create", "delete"
    original_content_hash: Optional[str]  # Hash of original content (for modify)
    new_content_hash: Optional[str]     # Hash of new content
    patch_diff: str                     # Unified diff or full content
    language: Optional[str]             # File type (python, javascript, etc.)
```

### 4.2 LLM Proposal Prompt Architecture

The LLM receives:
- Vulnerability finding details (category, component, evidence, severity)
- Root cause hypothesis
- Application structure context (affected files, relevant code snippets)
- Constraints from RemediationPolicy (max files, max patch size)

The LLM returns a structured `RemediationProposal` JSON matching the Pydantic schema.

### 4.3 Deterministic Proposal Validation

Before any file is modified:

1. **Schema validation**: Pydantic validates the `RemediationProposal` structure
2. **Policy validation**: `RemediationPolicy` checks file paths, patch sizes, forbidden operations
3. **Clone validation**: Proposal is applied to the clone (not production)
4. **Build validation**: Clone is built successfully after applying the fix
5. **Test validation**: Clone passes its test suite
6. **Red retest**: Red Agent attacks the remediated clone

## 5. Remediation Safety

### 5.1 RemediationPolicy

A deterministic validator that constrains what the LLM may propose. The LLM CANNOT bypass these rules.

```python
class RemediationPolicy(BaseModel):
    # File constraints
    allowed_paths: List[str]            # Relative paths the LLM may touch
    forbidden_paths: List[str]          # Paths the LLM must NEVER touch
    max_files_changed: int = 5          # Maximum files per proposal
    max_patch_size_bytes: int = 16384   # 16KB max patch per file
    max_total_patch_bytes: int = 65536  # 64KB total across all files

    # Execution constraints
    max_execution_time_seconds: int = 120
    max_memory_mb: int = 512
    max_remediation_attempts: int = 3   # Per finding

    # Content constraints
    forbidden_file_patterns: List[str]  # Regex patterns for forbidden files
    forbidden_operations: List[str]     # Operations the LLM cannot propose
    require_test_pass: bool = True      # Tests must pass after fix
    require_behavior_preservation: bool = True  # App must remain functional

    # Security constraints
    cannot_modify_infrastructure: bool = True   # No Dockerfile, CI/CD changes
    cannot_modify_security_controls: bool = True  # No auth, CORS, rate-limit changes
    cannot_remove_functionality: bool = True    # Cannot hide vuln by removing feature
    cannot_access_secrets: bool = True          # No secret file access
```

### 5.2 Forbidden Operations

The LLM MUST NOT:
1. Modify arbitrary files outside the allowed paths
2. Execute arbitrary commands
3. Access production or production secrets
4. Modify infrastructure (Dockerfile, CI/CD, deployment configs)
5. Disable security controls (authentication, authorization, input validation)
6. Remove functionality merely to make the attack fail
7. Bypass existing `PolicyEngine`, `SafetyBoundary`, `ActionIR`, or audit logging
8. Modify files in the `sentinelforge` codebase itself

### 5.3 Patch Size Limits

| Constraint | Default | Rationale |
| :--- | :--- | :--- |
| `max_files_changed` | 5 | Prevents sweeping, unreviewable changes |
| `max_patch_size_bytes` | 16,384 (16KB) | One file cannot be rewritten entirely |
| `max_total_patch_bytes` | 65,536 (64KB) | Total change must be reviewable |
| `max_execution_time_seconds` | 120 | Prevents hanging builds |
| `max_memory_mb` | 512 | Prevents resource exhaustion |
| `max_remediation_attempts` | 3 | Prevents infinite remediation loops |

## 6. Apply Remediation

### 6.1 CloneRemediationExecutor

```python
class CloneRemediationExecutor:
    """Applies remediation proposals to isolated clones. NEVER touches production."""

    def execute(
        self,
        proposal: RemediationProposal,
        clone: TargetClone,
        policy: RemediationPolicy,
    ) -> RemediationExecutionResult:
        # 1. Validate proposal against policy
        self._validate_proposal(proposal, policy)

        # 2. Snapshot clone (for rollback)
        snapshot = self._snapshot_clone(clone)

        # 3. Apply patches to clone
        changes = self._apply_patches(clone, proposal.patches)

        # 4. Build application in clone
        build_result = self._build_application(clone)

        # 5. Run application tests in clone
        test_result = self._run_tests(clone)

        # 6. Validate application still functions
        behavior_result = self._validate_behavior(clone)

        return RemediationExecutionResult(
            proposal_id=proposal.proposal_id,
            clone_id=clone.clone_id,
            snapshot_id=snapshot.snapshot_id,
            changes_applied=changes,
            build_passed=build_result.passed,
            tests_passed=test_result.passed,
            behavior_preserved=behavior_result.preserved,
            build_output=build_result.output,
            test_output=test_result.output,
        )
```

### 6.2 Patch Application Rules

1. Patches are applied ONLY to the clone filesystem
2. Each patch records the original file hash (for rollback)
3. After each file change, the change is recorded in an audit log
4. Build is triggered after ALL patches are applied
5. If build fails → automatic rollback to snapshot
6. If tests fail → automatic rollback to snapshot

### 6.3 Build & Test Execution

The build and test execution reuses the existing `SimulationAdapter`:
- Build: Execute build commands inside the clone container via `ContainerLinuxAdapter`
- Test: Execute test suite inside the clone container via `ContainerLinuxAdapter`
- All execution goes through the existing `SimulationWorker` → `PolicyEngine` → `ActionIR` → `SignedBlueprint` pipeline

## 7. Red Retest

### 7.1 Reusing Existing Red Agent

The Red Retest reuses the EXISTING Red Agent infrastructure. There is NO second Red Agent.

```python
class VulnerabilityRetestOrchestrator:
    """Orchestrates Red Agent retesting of a remediated vulnerability."""

    def prepare_retest(
        self,
        finding: VulnerabilityFinding,
        proposal: RemediationProposal,
        clone: TargetClone,
    ) -> RetestRequest:
        # Create RetestRequest for the existing Red Agent
        # The Red Agent will re-execute the original attack scenario
        # against the remediated clone
        ...

    def execute_retest(
        self,
        retest_request: RetestRequest,
        finding: VulnerabilityFinding,
        red_agent: RedAgent,
        clone_adapter: SimulationAdapter,
        before_outcome: ScenarioDetectionOutcome,
    ) -> VulnerabilityRetestResult:
        # 1. Red Agent replays the original attack against the clone
        # 2. If original attack is blocked, test relevant variants
        # 3. Return structured retest result
        ...
```

### 7.2 Retest Strategy

The retest proceeds in stages:

**Stage 1: Original Attack Reproduction**
- Red Agent re-executes the EXACT same attack scenario against the remediated clone
- Expected: Attack no longer succeeds (vulnerability eliminated)

**Stage 2: Variant Testing** (if Stage 1 passes)
- Red Agent generates relevant attack variants for the same vulnerability class
- Examples: For SQL injection, test different injection points, encoding bypasses
- Limited by `max_variants_per_retest` (default: 3)

**Stage 3: Regression Testing** (if Stage 2 passes)
- Application regression tests must still pass
- Application must remain functional (health check, core endpoints)

## 8. Verification Criteria

### 8.1 Deterministic Verification Rules

Verification is NOT "attack failed = automatically fixed." The following criteria must ALL hold:

```
VERIFIED requires ALL of:
  1. original_attack_blocked == True
  2. variants_blocked >= variants_tested * 0.8 (80% threshold)
  3. regression_tests_passed == True
  4. application_functional == True
  5. changes_applied == True (remediation was actually applied)
  6. build_passed == True (application builds successfully)
  7. iteration_count <= max_iterations

REMEDIATION_FAILED requires ANY of:
  1. build_passed == False after all attempts
  2. iteration_count > max_iterations AND original_attack_blocked == False
  3. remediation patch violates RemediationPolicy

REQUIRES_HUMAN_REVIEW requires ANY of:
  1. iteration_count > max_iterations (budget exhausted)
  2. behavior_preserved == False (functionality broken)
  3. rollback_failed == True (cannot restore to previous state)
  4. ambiguous_retest_result == True (inconclusive evidence)
```

### 8.2 Verification State Diagram

```
    Remediation Applied
         │
         ▼
    Build & Test
         │
    ┌────┴────┐
    │ Pass?   │
    │  YES    │ NO → ROLLBACK → next attempt or REMEDIATION_FAILED
    └────┬────┘
         │
         ▼
    Red Retest: Original Attack
         │
    ┌────┴──────────┐
    │ Blocked?       │
    │  YES            │ NO → ROLLBACK → next attempt or REMEDIATION_FAILED
    └────┬──────────┘
         │
         ▼
    Red Retest: Variants
         │
    ┌────┴──────────┐
    │ 80% blocked?   │
    │  YES            │ NO → next attempt or REMEDIATION_FAILED
    └────┬──────────┘
         │
         ▼
    Regression Tests Pass?
         │
    ┌────┴──────────┐
    │  YES            │ NO → REQUIRES_HUMAN_REVIEW
    └────┬──────────┘
         │
         ▼
      VERIFIED
```

## 9. Iteration Loop

### 9.1 Bounded Loop Design

```
    FINDING (iteration_count=0)
      │
      ▼
    PROPOSE FIX (LLM generates RemediationProposal)
      │
      ▼
    VALIDATE (RemediationPolicy)
      │
    ┌─┴──────────┐
    │ Valid?      │
    │  YES        │ NO → REJECT → next proposal or REMEDIATION_FAILED
    └─┬──────────┘
      │
      ▼
    APPLY TO CLONE
      │
      ▼
    BUILD & TEST
      │
    ┌─┴──────────┐
    │ Pass?       │
    │  YES        │ NO → ROLLBACK → increment iteration_count
    └─┬──────────┘
      │
      ▼
    RED RETEST
      │
    ┌─┴──────────────┐
    │ VERIFIED?       │
    │  YES → COMPLETE │
    │  NO  → iteration_count++ │
    │         │       │
    │    budget left? │
    │     YES → PROPOSE FIX again
    │     NO  → REMEDIATION_FAILED_REQUIRES_HUMAN_REVIEW
    └─────────────────┘
```

### 9.2 Budget Enforcement

```python
class RemediationBudget(BaseModel):
    max_iterations: int = 3             # Max fix attempts per finding
    max_llm_calls: int = 10             # Max LLM calls for remediation proposals
    max_wall_time_seconds: int = 600    # Max total time per finding
    max_variants_per_retest: int = 3    # Max attack variants per retest
    max_clone_lifetime_minutes: int = 30 # Max clone lifetime

    def assert_has_remaining(self, iteration: int, llm_calls: int, started_at: datetime) -> None:
        if iteration >= self.max_iterations:
            raise RemediationBudgetExhausted("Max remediation iterations reached")
        if llm_calls >= self.max_llm_calls:
            raise RemediationBudgetExhausted("Max LLM calls for remediation reached")
        elapsed = (datetime.now(timezone.utc) - started_at).total_seconds()
        if elapsed >= self.max_wall_time_seconds:
            raise RemediationBudgetExhausted("Max remediation time reached")
```

### 9.3 LLM Cannot Control Loop

The iteration loop is controlled entirely by deterministic Python code. The LLM:
- CANNOT decide to continue or stop the loop
- CANNOT modify budget limits
- CANNOT see or modify iteration counters
- CANNOT skip retest stages
- CANNOT declare a finding VERIFIED

## 10. Rollback

### 10.1 Snapshot-Based Rollback

Every remediation attempt creates a snapshot BEFORE applying patches. Rollback restores the clone to the snapshot state.

```python
class CloneSnapshot(BaseModel):
    snapshot_id: UUID
    clone_id: UUID
    version: int                        # Monotonically increasing
    created_at: datetime
    snapshot_type: str                  # "pre_remediation", "post_remediation"
    file_hashes: Dict[str, str]         # Path -> SHA-256 hash of each file
    container_snapshot_id: Optional[str]  # Docker snapshot ID
```

### 10.2 Rollback Process

```
Clone v1 (original, from source)
  │
  ├── Snapshot s1 (pre-fix-1)
  ├── Apply Fix #1
  ├── Build FAILS
  ├── Rollback to s1
  ├── Clone restored to v1
  │
  ├── Snapshot s2 (pre-fix-2)
  ├── Apply Fix #2
  ├── Build PASSES
  ├── Tests PASS
  ├── Red Retest: VERIFIED
  └── Clone stays at v2 (remediated)
```

### 10.3 Rollback Requirements

1. **Every attempt is reversible**: The clone MUST be restorable to any previous snapshot
2. **Audit trail preserved**: All snapshots and rollbacks are recorded for auditability
3. **Rollback failure = REQUIRES_HUMAN_REVIEW**: If rollback fails, the finding requires human intervention
4. **Production is NEVER involved**: Rollback only affects the clone, never the source target

## 11. State Machine Integration

### 11.1 Branch 1 vs Branch 2 Distinction

Branch 1 (Detection Gap) operates on `ExerciseStateMachine` for detection-rule remediation.
Branch 2 (Application Vulnerability) operates on `ExerciseStateMachine` for application-code remediation.

These are NOT parallel paths through the same states. Branch 2 introduces NEW states.

### 11.2 New Exercise States

```python
VALID_TRANSITIONS = {
    # ... existing Branch 1 transitions preserved ...

    # Branch 2: Application Vulnerability Remediation
    "VULNERABILITY_FOUND":     ["VULNERABILITY_ANALYZING", "COMPLETED"],
    "VULNERABILITY_ANALYZING": ["REMEDIATION_PROPOSED", "REQUIRES_HUMAN_REVIEW"],
    "REMEDIATION_PROPOSED":    ["REMEDIATION_VALIDATING", "REJECTED"],
    "REMEDIATION_VALIDATING":  ["CLONE_CREATING", "REJECTED"],
    "CLONE_CREATING":          ["REMEDIATING"],
    "REMEDIATING":             ["RETESTING", "ROLLING_BACK"],
    "ROLLING_BACK":            ["REMEDIATING", "REMEDIATION_FAILED"],
    "RETESTING":               ["VERIFIED", "REMEDIATING", "REMEDIATION_FAILED"],
    "REMEDIATION_FAILED":      ["REQUIRES_HUMAN_REVIEW", "COMPLETED"],
    "REQUIRES_HUMAN_REVIEW":   ["COMPLETED"],
}
```

### 11.3 State Transition Guards

Every transition is guarded by deterministic validation:

| Transition | Guard |
| :--- | :--- |
| `VULNERABILITY_FOUND → VULNERABILITY_ANALYZING` | `VulnerabilityFinding` must have `status == OPEN` and valid `evidence` |
| `VULNERABILITY_ANALYZING → REMEDIATION_PROPOSED` | `RemediationProposal` must pass Pydantic schema validation |
| `REMEDIATION_PROPOSED → REMEDIATION_VALIDATING` | `RemediationPolicy.validate()` must pass |
| `REMEDIATION_VALIDATING → CLONE_CREATING` | `ApplicationTarget` must exist and be authorized |
| `CLONE_CREATING → REMEDIATING` | `TargetClone` must be `READY` |
| `REMEDIATING → RETESTING` | `RemediationExecutionResult.build_passed == True` |
| `REMEDIATING → ROLLING_BACK` | `RemediationExecutionResult.build_passed == False` or `tests_passed == False` |
| `ROLLING_BACK → REMEDIATING` | `CloneSnapshot` restored successfully, `iteration_count < max_iterations` |
| `RETESTING → VERIFIED` | `VulnerabilityRetestResult.vulnerability_eliminated == True` |
| `RETESTING → REMEDIATING` | `VulnerabilityRetestResult.vulnerability_eliminated == False` AND `iteration_count < max_iterations` |
| `RETESTING → REMEDIATION_FAILED` | `iteration_count >= max_iterations` |

### 11.4 LLM Cannot Control Transitions

State transitions are driven exclusively by the `RemediationOrchestrator` Python code. The LLM:
- CANNOT directly transition the exercise state machine
- CANNOT emit state transition commands
- CANNOT skip validation steps

## 14. Security Threat Model

### 14.1 Threat Analysis

| Threat ID | Threat | Impact | Deterministic Mitigation |
| :--- | :--- | :--- | :--- |
| **T-B2-01** | Malicious remediation proposal | Modify unrelated files, inject backdoor | `RemediationPolicy` enforces `allowed_paths`, `max_files_changed`, `max_patch_size_bytes` |
| **T-B2-02** | Prompt injection in source code | LLM generates malicious fix | Patches are validated by `RemediationPolicy` before application; LLM never directly modifies files |
| **T-B2-03** | Path traversal in patch target | Modify files outside clone | `allowed_paths` whitelist + `forbidden_file_patterns` regex; path normalization |
| **T-B2-04** | Arbitrary command execution | Execute commands in clone | All execution through `SimulationAdapter` → `PolicyEngine` allowlist → `SignedBlueprint` |
| **T-B2-05** | Production targeting | Modify production application | `TargetAuthorizationValidator` blocks `PRODUCTION` environment targets from remediation |
| **T-B2-06** | Secret leakage | Extract production secrets | `original_secrets_excluded = True`; clone uses synthetic secrets only |
| **T-B2-07** | Malicious repository contents | Repository contains exploit code | Patches validated by `RemediationPolicy` before application; content scanning |
| **T-B2-08** | Destructive patches | Remove all code to hide vulnerability | `cannot_remove_functionality = True`; `require_behavior_preservation = True` |
| **T-B2-09** | Disable security controls to hide vuln | Remove auth to make attack fail | `cannot_modify_security_controls = True`; `require_test_pass = True` |
| **T-B2-10** | Infinite remediation loop | Exhaust resources | `max_iterations = 3` enforced by `RemediationBudget`; deterministic Python loop |
| **T-B2-11** | Cross-tenant clone access | Access another tenant's clone | `organization_id` mandatory on all queries; Docker network isolation |
| **T-B2-12** | Rollback failure | Clone stuck in bad state | `REQUIRES_HUMAN_REVIEW` if rollback fails; clone auto-expires |
| **T-B2-13** | Compromised clone | Clone used as attack platform | Clone has no outbound network; resource limits; auto-cleanup on expiration |
| **T-B2-14** | LLM bypasses RemediationPolicy | Modify files via crafted proposal | `RemediationPolicy` is deterministic Python, not LLM-controlled; schema validation |
| **T-B2-15** | LLM declares premature VERIFICATION | Skip retest stages | VERIFICATION requires `VulnerabilityRetestResult` object; Python code controls transitions |

### 14.2 Mitigation Stack

```
Layer 1: Schema Validation (Pydantic)
Layer 2: RemediationPolicy (deterministic Python)
Layer 3: Target Authorization (production = READ-ONLY)
Layer 4: Clone Isolation (Docker network, resource limits)
Layer 5: SimulationAdapter (existing security boundary)
Layer 6: PolicyEngine (existing allowlist)
Layer 7: BlueprintSigner (HMAC authorization)
Layer 8: Red Agent Retest (existing verification)
Layer 9: State Machine (deterministic transitions)
Layer 10: Budget Enforcement (deterministic limits)
```
