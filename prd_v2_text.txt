SentinelForge — PRD V2 & Architecture Revision
Continuous AI Purple Teaming • Adversarial Detection Validation • Detection Gap Remediation
Status: New source of truth after the architectural pivot. Phase 1 is complete. Phase 2 is implemented but final Docker E2E validation is blocked by the current Windows/Docker environment. Phase 3 must follow the revised architecture before implementation continues.
1. Executive Summary
SentinelForge is an AI-driven continuous purple-teaming platform. An autonomous Red Agent continuously explores diverse adversarial strategies against authorized, isolated cyber-range assets. Real runtime telemetry is collected and evaluated by the detection stack. When an adversarial behavior is detected, the result becomes evidence of coverage. When it is missed, SentinelForge creates a Detection Gap. A Blue/Analyst Agent analyzes the evidence and existing detection logic, proposes a detection improvement, validates it against malicious and benign evidence, and retests it. The Red Agent can then adapt and try another strategy.
Core loop: RED DISCOVERS → DETECTION OBSERVES → GAP IS IDENTIFIED → BLUE ANALYZES → DETECTION IS IMPROVED → RETEST PROVES THE CHANGE → RED ADAPTS.
2. Problem Statement
Fixed attack lists and periodic manual purple-team exercises can overfit a detection program to known test cases. A detection may recognize one representation of a behavior while missing another. Detection gaps are often discovered manually, and proposed fixes may not be empirically validated.
Static test catalogs cannot exhaustively represent adversarial behavior.
A successful attack simulation does not prove detection coverage.
Missed detections require investigation and detection-engineering work.
A new rule must be tested for both malicious coverage and false positives.
AI is useful only if its creativity is contained by deterministic safety controls.
3. Product Vision
Give an AI attacker freedom to explore adversarial strategies inside an isolated cyber range while keeping production and control-plane assets outside its execution boundary. Turn every experiment into measurable detection evidence and turn meaningful misses into validated detection improvements.
Product question:
Can an intelligent adversary find something our detection system misses—and if it can, can SentinelForge turn that failure into a validated detection improvement?

5. Goals
Continuously generate diverse adversarial scenarios for authorized security objectives.
Execute scenarios only inside isolated, explicitly authorized cyber ranges.
Capture real runtime telemetry.
Measure detection coverage and identify reliable Detection Gaps.
Use AI to analyze why a detection missed a behavior.
Generate candidate detection improvements.
Validate candidates against malicious and benign evidence.
Retest and empirically verify improvements.
Allow the Red Agent to adapt after detection changes.
Maintain durable evidence, audit trails, correlation and reproducibility.
Scale to multiple simulation adapters without redesigning the control plane.
6. Non-Goals and Safety Boundaries
No attacks against production assets.
No production credentials or unrestricted infrastructure credentials exposed to agents.
No unrestricted Internet egress from the attack range.
No Docker-socket access for the Red Agent.
No autonomous production deployment of detection changes.
No claim that the platform finds every possible attack or zero-day.
No acceptance of an AI claim without evidence and retesting.
No reliance on a single container as the only security boundary for high-risk autonomous testing.

9. Red Agent Requirements
Input: security objective, authorized range, current coverage, experiment history and constraints.
Output: adversarial scenario and execution plan, not unrestricted shell access.
Explore materially different strategies rather than selecting a fixed attack ID.
Prioritize unexplored detection space and avoid redundant experiments.
Adapt after detection improvements.
Propose a risk level; never authorize itself.
Remain outside the trust boundary for execution.
10. Experiment Safety Boundary
The safety layer protects the environment without artificially restricting adversarial creativity to a fixed attack catalog.
Authorized target identities and range membership.
Authorized network/subnet boundaries.
No production routes or credentials.
No uncontrolled Internet egress.
CPU, memory, storage, time and rate limits.
Privilege/capability restrictions.
Mandatory cleanup/reset.
Approval gates for high-risk experiments.
Full auditability of proposed, approved, rejected, executed and failed experiments.
Stronger VM/cloud isolation for higher-risk testing.

12. Telemetry and Detection
Falco provides real runtime/kernel telemetry in the Linux range.
Telemetry Collector remains unprivileged and has no Docker-socket access.
Raw Falco output is normalized into NormalizedEvent.
Telemetry is untrusted data and cannot issue instructions to agents.
DetectionResult links evidence to simulation/action/exercise identity when correlation is reliable.
Do not guess correlation; use NULL when evidence is insufficient.
Redis is transport, not source of truth.
PostgreSQL stores normalized events and detection results with bounded retention.

14. Blue Agent Requirements

Validate syntax/schema/deterministic behavior.
Test against malicious evidence.
Test against benign evidence to evaluate false-positive risk.
Retest the original adversarial scenario.
Accept remediation only after empirical success.

16. Required Changes to Completed Phase 1
Reframe the Policy Engine from an attack allowlist into an Experiment Safety/Authorization Boundary.
Keep exact-match bash controls as low-level safety invariants for currently supported shell actions; do not remove them simply to increase AI creativity.
Add SecurityObjective, AdversarialScenario, ExecutionPlan, RiskLevel and ExperimentConstraints domain concepts.
Keep ActionIR as the constrained execution representation produced after planning and safety validation.
Bind experiments to an authorized environment/range and tenant.
Add a durable policy-decision record explaining allow, deny or escalation.
Preserve HMAC, expiry, blueprint_id, replay protection, audit logging and tenant isolation.
Extend lifecycle states to cover experiment, detection-gap, remediation and retest flows without permitting direct VERIFIED manipulation.
Treat all LLM output and telemetry strings as untrusted.
17. Required Changes to Completed Phase 2
Keep SimulationWorker and its documented Docker-socket risk.
Introduce a SimulationAdapter interface so Web/API/DB/Windows/Cloud adapters can be added later.
Do not let the AI choose the final target; server-side policy resolves the actual authorized target.
Retain timeout and output limits.
Retain target hardening: non-root, dropped capabilities, no-new-privileges, read-only filesystem where compatible, and no Docker socket in the target.
Add mandatory cleanup/reset semantics.
Add range-level network and resource controls.
Use stronger VM/cloud isolation for high-risk autonomous experiments.
Finish real Phase 2 integration tests on Linux/native Docker before claiming complete E2E validation.
Test timeout behavior and cleanup with the actual target image.
18. Required Changes for Phase 3
Implement the revised telemetry architecture, not a fixed-attack-only pipeline.
Keep Falco privileged and Collector unprivileged.
Pin and verify Falco version.
Implement NormalizedEvent and DetectionResult with reliable correlation fields.
Use NULL rather than guessing correlation.
Use Redis only as transport and PostgreSQL as durable source of truth.
Perform Sigma compatibility spike before relying on matcher features.
Test malformed JSON, oversized events, malicious Unicode and prompt-injection telemetry.
Use native Linux or a suitable Linux environment for real Falco E2E; fixtures are for unit/integration tests.

23. Threat Model
Compromised Red Agent: must not reach production or obtain control-plane secrets.
Prompt injection through telemetry: telemetry remains evidence only.
Malicious generated scenario: deterministic safety boundary and range containment apply.
Compromised target: disposable and isolated; no production path.
Tampered blueprint: HMAC/expiry reject it.
Replay: durable blueprint claim rejects duplicate execution.
Compromised Worker: remains a high-impact risk; stronger isolation is a hardening priority.
Compromised Redis: treated as transport compromise.
Malicious candidate detection: cannot become accepted without validation and retest.
24. Claims We Will Not Make

SentinelForge automatically finds every zero-day.
The AI cannot be compromised.
Docker alone makes autonomous attacks completely safe.
An LLM-generated rule is automatically correct.
Passing tests proves complete security.
25. Positioning
SentinelForge should be presented as a continuous adversarial detection-validation platform, not as a generic AI penetration tester.
Core differentiator: AI-generated adversarial exploration + real telemetry + detection-gap reasoning + AI-assisted detection improvement + empirical retesting.

27. Final Architecture Statement
SentinelForge is not an unrestricted AI attacker. It is an AI-driven adversarial experimentation system operating inside a deliberately constrained cyber range. AI creativity exists above the deterministic safety boundary; execution, authorization, isolation, signing, replay protection, evidence and auditability remain deterministic. The product's value is the continuous challenge of the detection layer and the empirical conversion of detection failures into validated improvements.
